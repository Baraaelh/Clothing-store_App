# الأناقة الذكي — تطبيق الموبايل

تطبيق Flutter لمحلات الملابس، مربوط بباك اند **appStore API v1** (`/api/v1`). **يعمل بدون إنترنت**: البيانات تُنزّل إلى SQLite على الجهاز، وكل عملية تُحفظ محليًا ثم تُرسل للسيرفر تلقائيًا عند توفر الاتصال.

## الميزات

- **تسجيل الدخول:** باسم المستخدم وكلمة المرور، مع تسجيل الجهاز (UUID ثابت لكل حساب) وتوكن Sanctum في التخزين الآمن. الجلسة تعمل بعدها بدون إنترنت حتى تنتهي أو يرفضها السيرفر (401). تبديل الفرع لمن له أكثر من فرع.
- **الصلاحيات من السيرفر:** كل شاشة تظهر فقط لمن يملك صلاحيتها (البيع، الكتالوج، إدارة المنتجات، الشراء، التكلفة، الحد الأدنى للسعر).
- **البيع:** بحث بالاسم أو الكود أو SKU، المتاح لكل صنف (بعد خصم الحجوزات ومبيعات الجهاز غير المرسلة)، سلة، خصم على الفاتورة، دفع كامل أو جزئي أو آجل، اختيار حساب القبض (درج/بنك/محفظة) والزبون، وحساب الباقي. سجل فواتير الجهاز مع رقم فاتورة السيرفر بعد الاعتماد.
- **المنتجات:** قائمة وتفاصيل الأصناف (لون، مقاس، سعر، حد أدنى، رصيد)، إضافة منتج جديد بأصنافه، وتعديل الاسم والتصنيف والأسعار والتفعيل.
- **المخزون:** الرصيد والمحجوز والمتاح لكل صنف، فلترة (قليل/نفد)، قيمة المخزون بالتكلفة لمن يملك الصلاحية، و**استلام بضاعة**: فاتورة شراء من مورد مع دفعة اختيارية، أو بضاعة أول المدة قبل إغلاق فترة الإعداد.
- **عمليات المزامنة:** المنتظرة والمرفوضة مع سبب الرفض. البيع تحت الحد الأدنى يُؤكَّد من الشاشة نفسها، والبيع المرفوض لتغيّر الرصيد يُعاد بالرصيد الحالي، أو تُلغى العملية.

## التشغيل

```bash
flutter pub get
flutter run --dart-define=API_BASE_URL=https://store.example.com/api/v1
flutter test                       # اختبارات الوحدات
```

بدون `API_BASE_URL` تظهر شاشة الدخول برسالة أن السيرفر غير مضبوط.

### اختبار التكامل مع باك اند حقيقي

```bash
flutter test test/integration \
  --dart-define=BACKEND_URL=http://127.0.0.1:8000/api/v1 \
  --dart-define=BACKEND_USER=owner --dart-define=BACKEND_PASSWORD=...
```

يحتاج نسخة appStore تجريبية (MySQL مع Triggers المزامنة) فيها فرع البيع فيه مسموح، وحساب قبض ومورد ومنتج بكمية. يجرب: الدخول، التنزيل الأول، بيعتين بدون نت على نفس الصنف، إعادة إرسال عملية مقبولة (بدون تكرار)، رفض البيع بمراجعة رصيد قديمة، إنشاء منتج وشرائه، رفض تعديل بمراجعة قديمة، والخروج.

## البنية (Clean Architecture + Cubit)

```
lib/
├── app/                      # MaterialApp، الثيم، الشاشة الرئيسية (تبويبات حسب الصلاحيات)
├── core/
│   ├── config/               # عنوان السيرفر ومسارات API v1
│   ├── database/             # SQLite: جداول الـ Cache والـ Outbox وفواتير الجهاز
│   ├── network/              # ApiClient (Dio) + توحيد الأخطاء
│   ├── session/              # الجلسة والصلاحيات والتخزين الآمن
│   ├── sync/                 # Outbox، ChangeApplier، SyncEngine، SyncCubit
│   └── data/                 # البيانات المرجعية (حسابات، زبائن، موردون، ألوان، مقاسات)
└── features/
    ├── auth/                 # تسجيل الدخول والخروج وتبديل الفرع
    ├── pos/                  # البيع والسلة والدفع وسجل الفواتير
    ├── products/             # المنتجات: قائمة، تفاصيل، إضافة، تعديل
    ├── inventory/            # المخزون واستلام البضاعة
    └── operations/           # مراجعة العمليات المرفوضة
```

## كيف تعمل المزامنة

حسب عقد الباك اند (`docs/flutter-api-contract.md` في مشروع appStore):

1. **التنزيل:** أول مرة `POST /sync/bootstrap` ثم `POST /sync/pull` بالـ cursor حتى `has_more=false`. كل صفحة تُطبق على الـ Cache مع حفظ الـ cursor في transaction واحدة. عند 409/422 يُمسح الـ Cache ويبدأ تنزيل جديد، ولا يُمس الـ Outbox.
2. **الإرسال:** كل عملية (`sale.create`، `product.create`، `product.update`، `purchase.create`، `opening_stock.create`) تُحفظ في الـ Outbox بـ `operation_uuid` ثابت، مع أثرها المحلي في نفس الـ transaction. تُرسل على دفعات (20) إلى `POST /sync/push`، وتُطابق النتائج بالـ UUID:
   - `accepted` / `already_applied`: تُعتمد (رقم الفاتورة، مراجعات المخزون الجديدة).
   - `retryable` / `dependency_blocked`: تبقى بنفس الـ UUID والمحتوى، وتُعاد بعد انتظار متزايد.
   - `validation_failed` / `conflict_requires_review`: تنتقل للمراجعة ولا تُعاد تلقائيًا؛ التصحيح عملية جديدة.
3. **مراجعات المخزون:** كل سطر بيع يحمل `expected_revision` من آخر تنزيل. بيعة ثانية بدون نت على نفس الصنف تُربط بالأولى (`stock_revision_from` + `dependencies`)، فالسيرفر لا يقبل بيع قطعة غير موجودة.

بعد كل دورة تُحدّث حالة الفرع من `GET /operation-state` (هل البيع مسموح).

## إضافة نوع عملية جديد

1. أضف دالة تبني الـ payload وتستدعي `Outbox.enqueue` داخل transaction مع الأثر المحلي.
2. إن احتاجت أثرًا بعد قبول السيرفر أو رفضه، أضف `OperationHandler` وسجله في `SyncEngine` داخل `core/di/injection.dart`.

## غير مدعوم في هذه النسخة

حسب ما يوفره API v1 حاليًا: طلبات المتجر الإلكتروني، المرتجعات والاستبدال، سداد الموردين اللاحق، المصروفات، رفع صور المنتجات، وإضافة تصنيفات/ألوان/مقاسات جديدة (تُضاف من لوحة الويب).
